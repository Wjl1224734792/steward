# 维护与演进（maintenance）

本文件展开 SKILL.md 的「接手 / 维护 / 演进」模式，面向长期存活的仓库。

## 1. 接手存量仓库（Adopt）

目标：在不破坏的前提下，快速建立可验证的认知。

### 1.1 勘察（只读优先）

- 语言/框架/运行时版本；包管理与锁文件。
- 入口与运行方式；构建、测试、lint、类型检查命令。
- CI/CD 配置：实际跑什么、是否可信、最近是否绿。
- 目录结构与模块边界；公共接口与数据模型。
- 配置与环境变量；密钥来源（只看位置，不读值）。
- 部署方式、数据存储、外部依赖与第三方服务。
- 文档现状：README 是否可跑、ADR/设计文档是否过期。
- 所有权与流程：CODEOWNERS、分支保护、发布节奏、issue 模板。

### 1.2 跑起来

在隔离环境按 README 从零安装、构建、测试；记录每一步的实际结果与偏差。跑不通时先修文档或环境说明，不急着改业务代码。

### 1.3 基线报告

产出一页：

- 健康度：构建/测试/CI/依赖/文档/可观测性（红/黄/绿 + 证据）。
- 前 5 大风险：安全、数据、单点、无人维护的依赖、缺失的测试。
- 快速收益：文档修正、明显 bug、低风险依赖升级。
- 30/60/90 天计划：先稳态，再小步改进，不搞大重写。

### 1.4 接手纪律

- 前两周不做大规模重构；先加测试与文档，再动结构。
- 每次只改一个关注点；改动前确认没有他人在同一区域工作。
- 把"为什么这样"问清楚并记录，不把不理解当错误。
- 发现的问题进债务登记，按影响排序，不一次性全修。

## 2. 维护节奏

| 频率 | 检查项 | 完成标志 |
|---|---|---|
| 持续 | CI 绿；告警有人认领；依赖告警不积压；错误日志可查 | 主干可发布 |
| 每周 | flaky 测试；补丁/次要依赖；未关闭的高优 issue；债务 Top 3 | 周记录更新 |
| 每月 | 依赖审计与 EOL；死代码/重复；文档漂移；备份恢复抽检；性能基线；权限复核 | 月度报告 |
| 每季度 | 路线图复盘；重大版本升级；架构适配度；弃用执行；灾难恢复演练；测试套件健康 | 季度评审 |
| 每半年 | 许可证/合规；威胁模型；平台 EOL；成本；供应商复核 | 风险登记更新 |

节奏可按团队调整，但不能没有；没有节奏的维护等于等故障。

容量分配：每个迭代给新功能、维护/债务、运维/合规各留固定比例（例如 60/25/15）并保留缓冲；长期只做功能、不还债的团队，终会被债务拖停。

## 3. 健康扫描（八类）

1. **构建与 CI**：主干是否绿、构建时长、缓存与可复现性、失败是否有人看。
2. **测试**：覆盖率趋势（参考而非目标）、flaky 率、关键路径是否有测试、测试时长。
3. **依赖与安全**：已知漏洞、EOL 版本、无人维护的包、许可证冲突、锁文件漂移。
4. **文档**：README 命令可跑、架构图与代码一致、ADR 可追溯、onboarding 路径完整。
5. **可观测性**：日志是否可行动、关键指标与告警、追踪覆盖、值班手册。
6. **性能**：关键路径基线、回归检测、容量余量、慢查询/大包体。
7. **数据与备份**：备份频率、恢复演练、迁移脚本可回滚、数据保留与隐私。
8. **权限与密钥**：最小权限、离职/轮换流程、密钥是否入库、审计日志。

每类给出：信号 → 判定 → 行动 → 证据。扫描结果进维护报告。

## 4. 技术债管理

登记字段：ID、现象、影响、触发条件、负责人、预估成本、下一步、到期日、状态。

分级（影响 × 紧迫度）：

- **立即修**：安全/数据风险、阻塞交付、故障根因。
- **排期修**：可度量地拖慢交付或增加故障率。
- **顺手修**：碰到该文件时一并小改（不扩大范围）。
- **明确接受**：记录理由与复核日期，到期重新评估。
- **删除**：功能已死 → 删代码、删开关、删文档。

规则：

- 不登记 = 不存在；登记了不排期 = 自欺。
- 每个迭代预留固定比例（如 10–20%）给债务与维护，避免"永远排不上"。
- 还债也走完整流程：测试、验证、文档；不因为"只是重构"就跳过。
- 债务清单每季度复核一次，过期项必须重新决策。

## 5. 演进（Evolution）

### 5.1 立项

- 目标可度量：交付周期、故障率、成本、性能、合规。
- 范围与不变量：哪些行为/接口绝不能变。
- 阶段划分与回滚点；每阶段的验收标准。
- kill criteria 与止损方式。

### 5.2 重构

- 先补 characterization 测试锁定现有行为。
- 小步提交，每步可构建、可测试、可回滚。
- 重构与行为变更分开；需要同时做时，先重构再加功能。
- 完成后删除旧路径与兼容层，更新文档。

### 5.3 迁移（数据/平台/框架）

1. 盘点读写方与契约。
2. 设计双写/双读或影子流量；定义一致性校验。
3. 回填历史数据，dry-run 验证。
4. 灰度切换，监控差异；保留回滚开关。
5. 全量切换并观察；稳定后删除旧路径。
6. 记录迁移报告：范围、时间线、问题、回滚演练结果。

### 5.4 弃用

- 公告：替代方案、时间线、影响面。
- 警告：运行时/编译期警告、文档标注、changelog。
- 删除：至少跨 2 个次版本或 90 天（取较晚者），遵守仓库政策。
- 清理：删代码、配置、文档、测试与监控项。

### 5.5 架构适配度

每季度用少量可度量问题自检：改动一个功能要碰几个模块？新成员多久能提交第一个 PR？部署频率与失败率？关键依赖是否可替换？答案变差就立项，不靠感觉。

### 5.6 版本与支持窗口

长期项目要明确支持政策，避免用户停在无补丁的版本上：

- 支持的版本范围（如最近 2 个主版本）与安全修复承诺。
- 每个版本的 EOL 日期、升级路径与破坏性变更清单。
- 发布节奏（固定列车或按需）与 hotfix 政策。
- 旧版本至少保留一个可升级窗口；EOL 前公告并给出迁移指南。

## 6. 维护报告

模板见 `assets/maintenance-report.md`（相对技能根目录）。最少包含：周期、健康度、完成项、风险与债务、指标变化、下期计划、需要决策的事项。

## 7. 事故与复盘

- 止血优先：回滚/降级/关闭开关，先恢复服务再找根因。
- 无责复盘：时间线、影响、根因、检测方式、为什么没更早发现、行动项（负责人 + 日期）。
- 行动项必须有回归测试或监控守卫；没有验证方式的行动项不算完成。
- 同类事故第二次发生 → 升级为架构/流程问题，不只修代码。
