# 开发流程（development）

本文件展开 SKILL.md 的「新建 / 功能 / 缺陷 / 发布」四种模式。所有流程都遵守三条底线与第 7 节完成定义。

## 0. 规模与切片

| 规模 | 典型投入 | 要求 |
|---|---|---|
| S | < 2 小时 | 三行任务卡；直接实施；跑相关门禁 |
| M | 0.5–2 天 | 完整任务卡；必要时设计说明；拆成 2–4 个可验证切片 |
| L | > 2 天 | 简报 + 设计/ADR + 里程碑；按垂直切片交付，每片独立可验收 |

切片原则：每片能独立构建、测试、演示或回滚；优先垂直切片（端到端打通一小条），避免先铺完所有层再联调。依赖用显式顺序表达，不靠"到时候再说"。

## 1. 新建项目（Greenfield）

### 1.1 立项简报

回答（一页以内）：

- 问题是什么、谁用、现在怎么凑合。
- 成功标准：可度量的结果，不是功能清单。
- 非目标：首版明确不做的事。
- 约束：平台、预算、期限、合规、团队。
- 风险与 kill criteria：什么情况下停止或转向。

模板见 `assets/project-brief.md`（相对技能根目录）。

### 1.2 Walking skeleton（先打通，再长肉）

首个提交就要有：

- 可运行的入口与一条端到端路径（哪怕返回假数据）。
- 构建、测试、lint 命令；CI 在首个 PR 就绿。
- README：安装、运行、测试、目录说明。
- 配置与环境变量样例（不含真实密钥）；日志入口。
- 许可证与基本仓库卫生（`.gitignore`、格式化配置）。

### 1.3 垂直切片

每个切片包含：入口/UI（若有）、业务逻辑、数据访问、测试、文档。切片完成即演示、即验证、即可发布（哪怕功能未全）。不要先写"通用框架"再填业务；抽象等第三个重复出现再做。

### 1.4 加固

- 错误处理与边界校验；失败信息可行动。
- 鉴权/授权、输入校验、密钥管理、依赖审计。
- 可观测性：日志、指标、健康检查（按项目规模）。
- 性能预算与关键路径测量（若有 UI/API）。
- 可访问性与国际化（若面向用户）。
- 备份/恢复与部署回滚（若涉及数据或服务）。

### 1.5 发布就绪检查

- [ ] 全量门禁绿，CI 与本地一致
- [ ] README 从零可跑通（最好在干净环境验证）
- [ ] 版本号、CHANGELOG、许可证
- [ ] 配置/密钥文档化，默认值安全
- [ ] 部署步骤与回滚步骤演练过
- [ ] 已知限制与下一步写入文档

## 2. 功能开发（Feature）

1. **任务卡**：问题、AC、非目标、边界、风险、验证计划（`assets/task-brief.md`）。
2. **设计说明**（满足任一）：跨 3 个以上模块、改公共接口/数据模型、引入新依赖或新服务、预估 > 2 天。写清备选方案与取舍，必要时转 ADR。
3. **测试先行**：为每条 AC 写行为测试；先确认失败原因正确。
4. **最小实现**：一次只让一个测试变绿；不预设未来需求。
5. **回归**：跑相关测试与全量门禁；检查对既有行为的影响。
6. **文档**：README/API 文档/changelog/配置说明随改动更新。
7. **自审 diff**：见 SKILL.md 第 7 节。

AC 写法：

- 好："提交空表单返回 400 且错误信息含字段名""离线时队列保留并在恢复后重放一次"。
- 差："表单更友好""性能更好"（除非给出指标阈值）。

范围控制：实现中发现的新问题记录到"发现"清单；只有阻塞当前 AC 才扩展范围，并在任务卡注明原因。

## 3. 缺陷修复（Bug）

铁律：**没有复现不调试，没有验证不改代码。**

1. **复现**：固定输入/环境/步骤，连续两次得到同样的失败；不稳定先解决不确定性。
2. **缩小**：二分、最小输入、对比最近正常版本（`git log` / `git bisect`）；每次只改一个变量。
3. **假设**：一句话可证伪的根因假设；禁止无假设直接改代码。
4. **验证假设**：最便宜的实验（日志、断点、最小脚本）；与假设矛盾就回到第 3 步。
5. **修复**：回答"被破坏的契约是什么、为什么之前没发现、最小修复是什么"；不顺手重构。
6. **回归测试**：先红后绿；不可自动化时加监控/断言/校验，并记录手工步骤。
7. **记录**：根因、影响范围、修复方式、预防措施；同类问题第二次出现时补不变量测试。

严重度与响应（可按项目调整）：

- P0：数据丢失、安全事件、全站不可用——立即止血，回滚优先，事后复盘。
- P1：核心功能不可用——当天处理，先回滚/降级再修根因。
- P2：部分功能受损或有绕行方案——排期修复，记录债务。
- P3：外观/文案/低频问题——批量处理，不打断当前交付。

不可复现：列出已尝试的环境与输入，收集日志/追踪，加临时观测后再等复现；不要凭猜测改代码。

## 4. 发布（Release）

### 4.1 发布前

- [ ] 全量门禁绿（与 CI 同一套命令）
- [ ] 版本号按语义化版本递增；CHANGELOG 按 Added/Changed/Fixed/Removed 分类
- [ ] 迁移说明：数据、配置、API、行为变更；破坏性变更给替代方案与时间线
- [ ] 回滚方案：代码、数据、配置三方面；演练或至少 dry-run
- [ ] 特性开关/灰度策略（高风险变更）
- [ ] 监控与告警就位；发布窗口与通知对象确认

### 4.2 发布中

- 构建可复现的产物（锁文件、固定工具版本）；记录构建号/提交 SHA。
- 按既定顺序部署；每步做冒烟检查；失败立即停止并回滚，不带病继续。

### 4.3 发布后

- 冒烟 + 关键指标观察（错误率、延迟、业务指标）。
- 确认版本生效；更新状态/发布记录；通知相关方。
- 24–72 小时内回看告警与用户反馈；有问题按缺陷流程处理。

### 4.4 热修复

从发布标签拉分支 → 最小修复 + 回归测试 → 走加速但完整的门禁 → 发布补丁版本 → 合并回主干（merge 或 cherry-pick）。热修复不跳过测试，不夹带功能。

## 5. 示例：一个 S 级缺陷的完整闭环

**任务卡（三行）**

- 问题：导出 CSV 时金额列少两位小数，财务对账失败。
- AC：金额列输出两位小数；空值输出空字符串；导出 3 行样例与预期一致。
- 验证：`pytest tests/export/test_csv.py` + 手工导出样例；风险低，无需回滚方案。

**过程**

1. 复现：用固定订单数据导出，确认 `12.5` 应为 `12.50`。
2. 定位：格式化函数用了 `str()` 而非定点格式化；假设被最小脚本验证。
3. 修复：改格式化函数，不顺手重构导出器。
4. 回归：先加失败测试（断言 `12.50`），修后转绿。
5. 验证：目标测试 + 全量测试；贴命令、exit code、关键输出。
6. 落档：CHANGELOG 的 Fixed 增加一条；无需 ADR。
7. 交接：说明改动文件、测试、已知限制（货币符号仍由前端加）。

## 6. 检查表

功能：

- [ ] 任务卡与 AC 可观察
- [ ] 测试覆盖新行为与边界
- [ ] 相关与全量门禁复跑
- [ ] 文档/changelog 更新
- [ ] diff 无越界与调试残留

缺陷：

- [ ] 稳定复现
- [ ] 根因假设被实验验证
- [ ] 回归测试先红后绿
- [ ] 影响范围与预防措施记录

发布：

- [ ] 版本/changelog/迁移说明
- [ ] 回滚演练
- [ ] 冒烟与发布后观察
