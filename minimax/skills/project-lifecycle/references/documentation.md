# 文档治理（documentation）

本文件是 [SKILL.md](../SKILL.md) §10 的深化，管「文档怎么不长成屎山」。

**与同目录文件的分工**：[memory.md](memory.md) 回答「该不该记、记在哪、怎么不断链」；本文件回答「记下来之后怎么管」——分类、预算、拆册、读契约、版本与归档。同一条规则只在一个文件里定义，另一处只留指针。

## 0. 三句话总纲

1. **活文档管体积，记录文档管索引，基线文档管版本**——三类三种待遇；用一套规则管三类，必然崩。
2. **必读是设计出来的，不是喊出来的**：恒读部分靠体积预算保证读得起；条件必读靠计划与任务单点名；其余靠索引完备。
3. **能机检的别写进散文**：体积、索引、版本一致性、快照不可变交给脚本或清单；文档里只写人才能判断的事。

## 1. 三类文档，三种待遇

| 类 | 例子 | 生长方式 | 治理手段 |
|---|---|---|---|
| **活文档** | 仓库指令文件、README、文档索引、架构总纲、接口契约、页面设计、测试方案、执行步骤 | 原地修订，同一主题只一份 | 体积预算 + hub-and-spoke 拆册 |
| **记录文档** | 单条决策记录（ADR）、单篇评审记录、事故复盘、变更日志条目 | 只增不改，单条不可变 | 薄索引 + 归档轮转 |
| **基线文档** | 需求规格、接口契约、数据模型、冻结的设计节点、有冻结语义的测试方案 | 原地修订 + 里程碑快照 | 版本字段 + 修订记录 + 历史区快照 |

判不准就按更严一类处理：能快照就快照，能拆就拆。

## 2. 活文档体积预算

| 文档 | 建议预算 | 超限动作 |
|---|---|---|
| 仓库根/子目录指令文件（`AGENTS.md` 等） | 100 行 | 正文拆到规则目录或 `docs/`；入口文件只留 ≤1 行指针 |
| 根 `README.md` | 120 行 | 固定四节：定位 / 快速开始 / 当前状态 / 链接；其余链接出去 |
| 文档索引（`docs/README.md`） | 150 行 | 目录级索引 + 自动索引区块，不手写逐条记录 |
| 薄记忆层（`docs/project/*.md` 每件） | 120 行 | 只留摘要 + 链接，正文进正式文档 |
| 单册正式文档 | 400 行 | hub-and-spoke 拆册（§3） |
| hub / 索引册 | 150 行 | 只放跨域公共口径 + 分册目录表 |

- 上表是**默认值**，按仓库实际情况调整，并把最终数字写进仓库指令文件（否则没人遵守）。
- **存量项目先记基线**：把当前超限项记成清单，之后只减不增（ratchet）；不为了过线删内容，也不因为"历史遗留"放弃治理。
- 超过预算不是审美问题：恒读文件的体积直接决定每轮上下文开销，读不起就谈不上"必读"。

## 3. hub-and-spoke 拆册

```text
docs/03-契约/
├── API契约.md          # hub：基础约定 + 错误码号段 + 分册目录表（≤150 行，恒读）
├── API-订单.md         # 分册：一个业务域一册（≤400 行）
├── API-审批.md
└── API-事件协议.md
```

规则：

1. **按主题/业务域拆，不按时间拆**；严禁 `XX-v2.md`、`XX-新版.md`（版本写文档头与修订记录，见 §6）。
2. hub 保留：跨域公共口径 + 分册目录表（每行：分册｜覆盖范围｜状态）；分册头部回指 hub。
3. 拆册触发：超预算，或单文件覆盖 ≥3 个可独立变更的主题。
4. 拆册动作：出映射表 → 建分册 → 移动正文 → hub 补目录表 → 全局搜旧引用改指向 → 索引同步 → 跑自检清单。
5. 引用一律写 `文件.md §节`，不复制正文。

## 4. 读契约

### 4.1 文档头（frontmatter）

正式文档与规则文件头部加：

```yaml
---
read: always | dir | task | on-demand
scope: backend/**          # read: dir 时必填（生效目录）
budget: 400                # 可选，覆盖默认行数预算
status: active | archived  # 归档/快照必须 archived
version: v2.1              # 基线文档必填，形如 vX.Y 或 X.Y
baseline: true             # 基线文档标记（有冻结语义者）
superseded-by: ../PRD-xxx.md   # 仅历史快照
---
```

| 字段 | 取值 | 约束 |
|---|---|---|
| `read` | `always` / `dir` / `task` / `on-demand` | 四档含义见 §4.2；缺省按 `on-demand` |
| `scope` | 目录 glob | `read: dir` 时必填 |
| `status` | `active` / `archived` | `archived` 必须在历史区或归档区 |
| `version` | `vX.Y` / `X.Y` | 基线文档必填 |
| `superseded-by` | 相对路径 | 只出现在历史快照，且目标必须存在 |

硬规则：

- **宿主原样注入的指令文件（`AGENTS.md` 等）不要加 frontmatter**——多数宿主把它当纯 markdown 注入，元数据会破坏注入效果；它的读契约由 §4.2 的索引表承载。
- 载体不支持 frontmatter 时（纯文本 wiki、issue 模板），用文档头部一张表等价承载同样的字段，不要直接放弃契约。

### 4.2 三级读契约

| 级 | 内容 | 触发 | 保障 |
|---|---|---|---|
| **R0 恒读** | 仓库指令 + 不变量/红线 + 薄记忆层 | 每轮 | 体积预算（读得起才谈必读） |
| **R1 条件必读** | 进目录 → 该层指令与规则；改契约 → 对应分册；任务命中 → 计划点名的文档 | 目录 / 任务 | 仓库指令里的「改什么 → 必读什么」表；计划字段点明；交付前核对 |
| **R2 按需** | 其余全部 | 自行检索定位 | hub / 索引完备 + 死链检查 |

**排计划时的硬要求**：跨模块任务在计划里给每个任务写「必读文档清单」（路径必须真实存在，且不能指向历史区）。

### 4.3 读长文协议

1. 先读 hub / 索引 → 再用检索定位到节 → 最后按偏移片段读。**禁止整文件倾倒**。
2. 实现任务**禁读**历史快照与归档区（那不是现行口径）；只有溯源/审计任务可读，且结论必须回指现版。
3. 交付/回复开头保留一行「对齐文档：`<文件>` §`<节>`」，让口径可核对。

## 5. 记录文档三铁律与 ADR

1. **单条不可变**：一条评审/一个决策一份（或总集内一节），历史正文不改；修订 = 补记或新条取代旧条（旧条标"已被 `<新条>` 取代"）。
2. **薄索引恒在**：每条一行（编号｜日期｜主题｜结论/状态｜链接）。恒读索引，按需点开单条。
3. **归档分层**：按季（或按版本线）轮转进 `archive/`；索引只留近期 + 一条归档链接。

**ADR 细则**：`ADR-000X-<标题>.md` 一号一文件，头部写 `> 状态：提议 | 接受 | 拒绝 | 已落地 | 已废弃`、`> 日期`、`> 决策者`；正文五节：背景 / 决策 / 备选方案 / 后果 / 参考（模板 [decision-record.md](../assets/decision-record.md)）。索引里每条状态必须与文件头一致（双向核对）。

**治理目录**（记录与索引的落脚处）的根层只放活文档与索引；任何单条记录落在根层都算违规。

## 6. 版本快照与溯源

### 6.1 模型：现版原地改，基线冻结才快照

```text
docs/01-需求/
├── PRD-xxx.md               # 现版 v2.1：路径永远稳定，SSOT，原地修订
├── FRD-xxx.md
└── history/                 # 快照区（不可变）
    ├── README.md            # 版本索引：版本｜日期｜摘要｜依据｜快照
    ├── manifest.json        # sha256 清单（不可变性机检）
    └── PRD-xxx-v2.0.md      # 旧基线，头部「已被 v2.1 取代 → 现版链接」
```

| 决策 | 取法 | 理由 |
|---|---|---|
| 现版路径 | 永远不带版本号 | 保住「同一主题只一份」与全部既有链接 |
| 快照时机 | **仅基线冻结**（范围/验收标准/契约口径等 major 变化）；澄清、笔误、补充说明不拍 | 细粒度历史交给版本控制（免费且完整），快照只管语义里程碑 |
| 快照性质 | 不可变 + 目录级索引 | 是留痕，不是第二事实源 |
| 与版本控制分工 | 版本控制 = 逐提交；快照 = 不装版本控制也能读的里程碑 | 交接 / 导出 / 审计不断链 |

### 6.2 修订记录表（现版尾部；超预算再拆独立文件）

```markdown
## 修订记录
| 版本 | 日期 | 变更摘要（条目编号） | 依据（拍板留痕） | 拍板人 | 快照 |
|---|---|---|---|---|---|
| v2.1 | 2026-11-12 | FR-3.2 审批阈值 100→500；新增 FR-7 | ADR-0012 + 评审记录-20261110 | 用户 | history/PRD-xxx-v2.0.md |
```

铁律：

1. **条目编号（FR/FP/错误码）永不复用、永不重排**；废弃标 `deprecated@v2.1`。编号是跨版本溯源的主键。
2. **依据三选一必填**（决策记录 / 评审记录 / 拍板记录）——修订行就是"不拍板不动文档"的落档终点。
3. **关键引用可钉版本**：`PRD.md §FR-3.2（v2.0 基线）`。现版改口径时，钉版本引用会立刻暴露"需重算"，而不是静默漂移。

### 6.3 双向溯源

- **正向**（口径何时/为何变）：现版修订表 → 修订行 → 依据链接看拍板过程 → 快照看旧基线原文。
- **反向**（某个交付时点的基线）：交付记录里记当次对齐的文档版本 → 版本索引按版本/日期定位快照。
- **联动**：交付记录的「文档更新清单」带一列版本 bump（vX.Y→vX.Z），工件与文档版本互锚。

### 6.4 手工快照 SOP（没有脚本时）

1. **先快照、后改口径**：把现版复制为 `history/<名>-v<旧版>.md`，头部写「已被 v<新版> 取代 → 现版链接」，`status: archived` + `superseded-by`。
2. 版本索引 `history/README.md` 加一行（版本｜日期｜摘要｜依据｜快照）。
3. 清单文件记下快照的 sha256（`sha256sum` / `shasum -a 256` / `certutil -hashfile`）。
4. 现版 bump 版本号，修订记录表加一行（依据必填）。
5. 校验三处一致：文档头 `version` = 修订表最新行 = 版本索引最新行；历史区文件哈希与清单一致。
6. 快照文件**禁止手改**；要改就重做快照并留痕。

## 7. 运行时工件与长期文档的边界（最容易错）

- **run 级报告不进长期文档**：实施报告、QA 报告、评审报告、浏览器/接口证据留在工件目录（如 `tmp/<run>/`、`.<工具>/<run>/`），它们是 T2 工件。
- **只有「阶段门禁评审」才写进治理目录**——那才是需要跨版本留存的东西。
- 别把所有评审都往文档里倒：索引会被稀释，检索会变慢，漂移概率上升。
- 工件目录随任务结束可清理；需要在文档里留痕时，只留**结论行 + 工件路径**。

## 8. 自检清单（没有门禁脚本也能做）

| # | 检查 | 判定 |
|---|---|---|
| 1 | 体积预算 | 每篇活文档是否在预算内？超了是否已拆册而不是硬塞？ |
| 2 | 读契约字段 | 都有 `read`？`dir` 是否带 `scope`？`archived` 是否在历史/归档区？ |
| 3 | 入口文件纯净 | 宿主原样注入的指令文件是否无 frontmatter、无长正文、只留指针？ |
| 4 | 记录分层 | 治理目录根层是否只有活文档与索引？单条记录是否一条一文件？ |
| 5 | 索引完备 | 每篇记录/快照在索引里有且仅有一行？有没有死链？ |
| 6 | ADR 双向 | 索引里每条状态与文件头状态一致？ |
| 7 | 版本三处一致 | 文档头 `version` = 修订表最新行 = 版本索引最新行？ |
| 8 | 快照不可变 | 历史区文件哈希与清单一致？有没有人手改过？ |
| 9 | 现版唯一 | 同一主题是否只有一份现版？历史区文件是否都标了 `superseded-by`？ |
| 10 | 修订行有依据 | 每条修订行是否挂了决策/评审/拍板链接？ |
| 11 | 计划必读可达 | 计划里点名的必读文档真实存在，且没有指向历史区？ |

存量项目：先把超限项与缺依据项记成基线清单，之后只减不增；不要为了让清单变绿而删检查项。

## 9. 反模式

| 反模式 | 症状 | 正解 |
|---|---|---|
| 三类文档一套规则 | 记录越堆越长、活文档没人拆 | §1 分治 |
| 按时间拆册 / 版本号进文件名 | 多份"现版"互相打架 | 现版路径稳定 + 历史区快照（§6） |
| 指令文件塞长正文 | 每轮注入开销爆炸、模型忽略红线 | 正文外移，入口只留 ≤1 行指针 |
| 快照手改 | 哈希不符、审计失真 | 禁止手改；重做走留痕 |
| 把历史区当现行口径 | 实现按旧基线漂移 | 实现任务禁读；快照头 `superseded-by` 弹回现版 |
| 所有评审都往文档倒 | 文档变垃圾场、索引膨胀 | 只有阶段门禁评审进文档；run 报告留工件目录 |
| 归档后忘了索引 | 索引断链、检索不到 | 归档即更新索引；先改索引再移文件 |
| 修订行不挂依据 | 溯源断链、AI 私改无法追责 | 依据三选一必填 |
| 编号重排/复用 | 跨版本溯源错位 | 编号唯一永久，废弃只标记不复用 |
| 为了过门禁删/弱化检查 | 治理失效 | 记基线只减不增（ratchet），不删检查 |

## 10. 落地清单

**新项目**：定三类划分 → 按预算写入口文件与索引 → 给每篇文档加文档头 → 建治理目录与历史区骨架 → 跑 §8 自检 → 再进实现。

**接手存量**：先盘点映射（哪些是活/记录/基线）→ 记基线清单（超限、缺依据、死链）→ 治理目录分层改造 → 重建索引 → 自检清单允许基线内超限 → 逐批 burn-down。

**每次交付收尾**：按三类落档 → 版本 bump 与修订行 → 索引/归档同步 → 过 §8 自检（或跑仓库的文档门禁）→ 在交付记录里写文档更新清单。
