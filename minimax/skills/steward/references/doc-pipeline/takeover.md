# 接手存量项目 SOP（盘点 → 映射 → 定位 → 补约束 → 门禁 → 常规流水线）

> 适用：接手他人代码、老项目规范化、并购/外包技术尽调、把「能跑但没有工程约束」的项目纳入流水线管理。
> **红线：先盘点后动手，不先做大改**（未知依赖多，外科手术式修改）；**需拍板项不私改**；盘点结论必须带 `file:line` 证据。

## 第 1 步：现状盘点（半天~1 天）

通读顺序：README / 现有文档 → 包管理清单（依赖与栈）→ 门禁配置 → 目录树 → 入口代码 → 测试现状。

产出《现状盘点表》（先放对话给用户，确认后落 `docs/07-治理/执行步骤.md`）：

```markdown
| 维度 | 现状 | 证据（file:line） | 风险/缺口 |
|---|---|---|---|
| 技术栈与版本 | | package.json / go.mod / pyproject… | |
| 目录结构与分层 | | | 分层混乱？循环依赖？ |
| 现有文档 | <清单：路径+主题+新旧> | | 与代码一致？ |
| 数据库/迁移 | | | 有无迁移管理？物理外键？ |
| 测试与门禁 | | | 覆盖率？门禁有无？ |
| 部署方式 | | | 可回滚？ |
| 可观测性 | | 抽样日志输出/监控配置 | 日志是否结构化？有无 trace/请求 ID 贯穿？告警落在哪？日志含 PII？留存有界？ |
| 安全（认证/权限/PII） | | | 权限收口点在哪？ |
| 现行编码风格 | | 抽样 3-5 个代表文件 | 与通用基线差异 |
```

## 第 2 步：文档映射（迁移需拍板）

现有文档按七阶段归类，出映射表：

```markdown
| # | 现文件（路径） | 目标落位（docs/01~07） | 阶段 | 备注（新旧/冲突） |
```

- 映射表给用户确认，**拍板后**才执行迁移（SOP 见 `sync-rules.md`：建目录 → git mv → 索引 → 互引 → 全局搜旧路径）。
- 无对应目录类型的文档：归入最接近的阶段目录，或提请新增 `04-专项/` 类目录。
- 明显过期文档：不删，标「已废弃」并在评审记录列需拍板项（是否归档/删除由用户定）。

## 第 3 步：阶段定位与差距检查

按七阶段判定「项目走到哪」，列缺失清单：

| 阶段 | 判定依据 | 常见缺口 |
|---|---|---|
| ① 需求 | 有无 PRD + FRD（功能需求）、验收口径 | 只有口头需求 → 补最小 PRD（范围+核心 FR+AC）；有 PRD 无 FRD → 按 FR 抽最小 FRD（FP 清单 + 字段/规则/异常 + AC 映射） |
| ② 架构 | 有无架构文档、目录结构是否体现分层 | 结构在代码里但无文档 → 逆向补架构设计.md + {X}工程化.md；**无横切域文档（安全/可观测性）→ 按 `templates/OBSERVABILITY.md` 补** |
| ③ 契约 | 有无 API/数据模型文档 | 最常见缺口：接口全靠读代码 → 从路由/ORM 逆向生成契约初稿 |
| ④ 实现 | 代码分层质量 | 屎山热点标记，不立即重构 |
| ⑤ 质量 | 测试/门禁/覆盖率 | 无门禁 → 先配最小门禁链（lint+test+build） |
| ⑥ 部署 | 部署脚本/回滚 | |
| ⑦ 治理 | ADR/执行步骤/索引 | 全缺 → 本 SOP 第 4-6 步补齐 |

## 第 4 步：补约束层与规范（一次到位）

1. **根 `AGENTS.md`**：红线从**现行代码提炼实际生效的约定**（认证方式、权限收口点、分层惯例、禁改区），不凭空发明；骨架见 `agents-files.md` §2。
2. **子目录 `AGENTS.md`**：现存各模块目录补局部规则（骨架见 `agents-files.md` §3）。
3. **编码规范**：按 `coding-standards.md` 四步生成——条款写进根/层级 `AGENTS.md`，长正文拆 `.agents/rules/`（全局 + 层级）并设必读引导；**尊重现有风格**（现状/目标/棘轮收敛三段式）。
4. **`docs/README.md`** 文档地图：每份文档一行（路径 | 主题 | 状态：权威/过期/待评审）。
5. 产品 harness 目录如需指向根 AGENTS.md → **提请用户配置**，AI 不代改。
6. **可观测性基线**（存量项目最高性价比的横切补齐）：按 `templates/OBSERVABILITY.md` 补 `docs/02-架构/可观测性*工程化.md`——先写「审计留痕 vs 运行日志」边界与关联 ID 贯穿链，再收日志字段与告警三要素；存量系统常缺，且补文档不影响现有代码运行（后续按棘轮收敛实现）。

## 第 5 步：门禁评审（首次）

按主 README.md §6.4 出 `docs/07-治理/评审记录-YYYYMMDD-接手盘点.md`：
- **结论先行**：当前处于阶段 X；可否进入下一阶段；
- 机械修复项（文档过期回填、索引缺失、渲染错误）→ 可直接修；
- 需拍板项（架构分歧、废弃文档去留、重构优先级、安全债）→ 列选项等用户拍板。

## 第 6 步：进入常规流水线

- `docs/07-治理/执行步骤.md` 建**三张表**：现状盘点（第 1 步产物落档）+ 剩余工序（按依赖排序，每项有验收标准）+ 开放项台账（散落各文档的待定/待拍板项统一编号 OP-xx 归口）——模板见 `templates/EXECUTION-STEPS.md`。
- 剩余工序跨多模块/多端时，同步起草 `docs/07-治理/开发顺序.md`（开工顺序 SSOT：依赖链 + 波次拆分 + 并行规则 + 估算，模板见 `templates/DEV-ORDER.md`）；已冻结的契约可直接排活。
- 之后一切改动走主 README.md §4 联动表 + §6 管理规范；新需求走 §5.4 变更入口；新功能一律 TDD。
