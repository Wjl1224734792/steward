# 系统化调试（systematic-debugging）

铁律：**没有复现不调试，没有验证不改代码**。修一个说不通的问题是靠运气，运气修出来的东西下个版本会再坏。

## 五步

1. **复现**：先造出确定性的失败（命令 / 输入 / 日志）。跑两次结果不同 → 先解决不确定性（数据、时序、环境），不谈根因。连续 2 次无法复现 → 停，列出需要补充的信息，不猜。
2. **缩小范围**：二分——注释/跳过一半逻辑、构造最小输入、对比最近一次正常的版本（git log / bisect）。每一步只改一个变量。
3. **提假设**：用一句话写出可证伪的假设（「X 在 Y 条件下返回了 Z，因为 …」）。禁止没有假设就直接改代码。
4. **验证假设**：设计最便宜的实验证伪它（打印、断点、最小复现脚本）。实验结果与假设矛盾 → 回到第 3 步，不加固错误假设。
5. **根因与修复**：回答三个问题再动手——被破坏的不变量/契约是什么？为什么之前没被发现？最小修复是什么？修复时禁止顺手重构。

## 产出要求

- 修复报告必须含：复现方式、根因（指向具体代码位置）、假设被验证的证据、为什么之前没发现。
- 回归测试先红后绿；不可自动化时说明原因并加守卫（监控/断言/校验）。
- 同一区域第二次出同类 Bug → 主动提出回填 CONSTITUTION/不变量测试，不要只修眼前的。
