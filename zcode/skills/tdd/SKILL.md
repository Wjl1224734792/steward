# TDD（tdd）

循环只有三拍，顺序不能换：**红 → 绿 → 重构**。

## 红灯：先写会失败的测试

- 测试写的是**行为契约**（输入 → 期望输出 / 可观察效果），不是实现细节（私有方法名、内部调用顺序）。
- 修 Bug 时：先用测试复现 Bug（它必须失败，且失败方式与线上现象一致），再修——可复现的 Bug 没有失败测试不修。
- 一次只加一个测试；跑一遍确认它**因预期原因失败**（断言失败而不是语法错/导入错——后者不算红）。

## 绿灯：最小实现

- 写刚好让测试过去的**最少代码**；不预设后面要的功能。
- 仓库无测试先例：先搭最小测试脚手架（沿用仓库既有框架与风格），这本身也是交付物。
- API/框架行为拿不准：先查证（Context7 / 官方文档 / 仓库依赖源码）再写测试，别把臆造的 API 行为写进契约。

## 重构：测试保持绿

- 消重复、提命名、理分层——每改一步跑一次测试。
- 重构不改变行为：如果重构让你想改断言，先停下来，那是行为变更，走需求/派单流程。

## 纪律

- 测试改动必须在计划 testChanges 里声明理由（反作弊）；禁止靠跳过/弱化断言变绿。
- 完成时：全量相关测试绿 + 报告贴真实输出（红的证据在修 Bug 时保留）。
- 测试只有绿没有红过 → 说明它可能恒真，自查断言是否真的约束了行为。
