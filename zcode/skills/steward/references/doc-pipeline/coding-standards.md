# 项目编码规范生成指南（从通用基线到项目版）

> 初始基线：本技能 `assets/coding-guidelines-baseline.md`（语言无关全域规范）。**基线是起点不是终点**——直接照抄会得到一份「全是项目用不到的语言、没有项目自己的架构约束」的无效规范。目标是生成**项目规范条款**：写进其生效层级的 `AGENTS.md`（全局→根，层级→子目录）；正文过长拆 `.agents/rules/*.md`，AGENTS 留摘录 + 必读引导。**规范不做成 skill**——skill 承载工作流（触发才加载，会漏生效）；规范是约束性条款，必须随层级稳定生效。

## 0. 落位结构（条款进 AGENTS，正文进 rules）

| 内容 | 落位 | 示例 |
|---|---|---|
| 全局规范条款（可判定，每条 ≤1 行） | 根 `AGENTS.md` 规范/红线段 | 「核心功能必须测试先行（细则：`.agents/rules/coding-standards.md` §3）」 |
| 全局规范正文（完整展开） | `.agents/rules/coding-standards.md` | TDD/命名/错误处理/门禁链完整条款 |
| 层级规范条款 | 对应子目录 `AGENTS.md` | `backend/AGENTS.md`：「禁反向依赖（细则：`.agents/rules/backend.md` §2）」 |
| 层级规范正文 | `.agents/rules/<层级>.md`（每代码层级 1 份，按目录命名） | backend.md / frontend.md / agent.md |

- rules 文件头 frontmatter 声明作用域：`description`（一句话）+ `globs`（适用路径，如 `backend/**`）。支持 rules 机制的 harness 自动匹配加载；不支持的靠 AGENTS 必读引导。
- 拆分原则：语言无关的通用条款→全局；特定栈/框架/架构条款→对应层级；**全局篇不肥大、层级篇不复制全局篇**（引用不复制）。
- AGENTS 只留摘录（红线 ≤5 条）+ 必读指针，不塞正文（根文件 ≤100 行）。

## 1. 基线覆盖域（裁剪时的检查清单）

| 域 | 基线章节 | 要点 |
|---|---|---|
| 开发环境 | §1 | 中文文档/注释；.editorconfig；.gitignore |
| 注释与文档 | §2.1 | 只写 Why 与边界；各语言文档格式映射 |
| 嵌套/不可变/模块化 | §2.2-2.4 | ≤4 层卫语句；返回新集合；命名导出禁循环依赖 |

| 质量保障 | §3 | 文档同步；tmp/ 临时文件；门禁链 Lint→TypeCheck→Test→Build→Dev；UI 实看调试；门禁覆盖率 ≥80% |
| 命名/错误处理 | §4-5 | 见名知义；布尔 is/has；禁空 catch；外层友好内层详细 |

## 2. 四步生成法

### 第一步：按栈裁剪
- 读架构文档选型表，确定项目实际语言/框架/ORM/包管理器。
- 基线中多语言映射表**只保留项目用到的行**（纯前端项目删 Go/Rust/Java 行，Python 后端删 C# 行）。
- 不适用整节删除（如后端项目删 §2.9 前端样式；无 Tailwind 删 @apply 条款）。
- 规范文件 frontmatter 按项目写：`description` 一句话摘要（含项目名 + 技术栈）、`globs` 声明适用范围；条款按 §0 落位到对应层级 AGENTS。

### 第二步：按架构补充项目专属条款
从 `docs/02-架构/架构设计.md` 与 `{X}工程化.md` 提炼，写成可判定规则：
- 分层边界与依赖方向（如：endpoints 薄封装 / services 承载业务 / 禁反向依赖 / 禁跨层调用）。
- 项目禁止模式（如：Agent 层禁直连数据库、禁信任请求体中的租户/用户标识、PII 必须走脱敏函数）。
- **数据访问条款**（ORM 项目必生成，标准全文见 README §3.8 口径 + `data-access.md`）：表结构以 ORM schema 为唯一事实来源（迁移从 schema 生成，禁手写 DDL 平行定义）；查询构建器优先、复杂查询用参数化 sql；禁 `sql.raw()` 与字符串拼接 SQL；动态标识符走白名单；复杂 SQL 入仓储层并测试（含行级隔离/权限过滤断言）。
- 项目约定目录与别名（`@/` 指向、模块归属规则）。
- **横切域条款**（从 `docs/02-架构/` 对应横切文档提炼，如可观测性）：日志字段字典/级别语义/关联 ID 贯穿 → 全局条款 + 各层级补充（网关/服务/前端/Agent 各写各的落点）；**跨端口径**（trace 头名、错误信封字段、审计关联列）同时落契约文档一行，缺一即漂移。
- 领域规则实现要求（如：参数一律配置化 + 生效日期，禁写死魔法数字；金额用 decimal 不用 float）。
每条注明权威来源（`docs/… §x`），与文档冲突时以文档为准并回报。

### 第三步：TDD 强制条款（用户级红线，必须保留）
- **需要的功能/核心业务逻辑：先写测试再实现**（红 → 绿 → 重构）；不允许「先实现后补测试」。
- 每个测试只验证**一个行为**；命名 `应该_预期行为_当_条件`。
- 有明确数字边界的领域规则（费率/上限/阈值/日期口径）建**黄金集**用例表，与 `docs/06-测试/` 同源。
- 例外：UI 快照、探索性原型不强制 TDD，但关键流程仍须有测试；例外须注释说明。
- 修 bug：先写复现测试（红），再修（绿）。

### 第四步：能落本地门禁的先落本地门禁
- 机检项沉门禁：lint 规则（零警告或棘轮：警告数不得增加）、typecheck、覆盖率阈值（整体 ≥80%，核心业务 ≥90%）、禁调试语句/禁硬编码密钥扫描。
- 规范文档只留机检不了的（架构判断、命名语义、评审要求）。
- 质量门禁链固定顺序：**Lint → TypeCheck → Test → Build → Dev（先杀旧进程再启动）**，前一步失败不进下一步。

### 命名补充：编码 What，不编码 When（生成规范时必写一条）
- 目录 / 文件名回答「这是什么」，不回答「第几批」。波次 / 子批 / 工单 / 优先级编号（`W1` `w7.2` `S3` `OP-142` `P1` `篇二十七` `第3批`）**一律不进代码产物名**（源码 / 测试 / 迁移目录 / 种子 / 脚本 / E2E / 性能脚本）。
- 正反例：`attendance.foreman-scope-convergence.test.ts` ← `w8s4.op142.foreman-convergence.test.ts`；`<时间戳>_overtime_remark/` ← `<时间戳>_w7_2_overtime_remark/`；`dashboard.spec.ts` ← `w6-dashboard.spec.ts`；`seed-dashboard-demo.ts` ← `seed-w6.ts`。
- 阶段归属写进度 SSOT（执行步骤）与评审记录；commit message 可带波次（历史坐标），文件名不带（长期资产）。
- 允许：编号本身是业务标识符的（报表 `R1~R8`、状态枚举、`S3`、`k6`、`h5`、`v1`）；文档层标识（ADR / 评审记录日期 / `GT-xx`）不受代码命名约束，但 `GT` / `OP` 编号禁进代码文件名——避坑写法是写进用例名或文件头注释。
- 落机检：**新项目**直接上 filename guard（零容忍）；**存量项目**用棘轮基线 —— 已应用迁移进 `[FROZEN]`（改名会造成迁移漂移），其余存量进 `[BURN-DOWN]`，守卫对「新违规」与「已失效条目」双红灯，强制只减不增。脚本与 SOP → `naming-guard.md`。

## 3. 生成时机

| 场景 | 时机 | 注意 |
|---|---|---|
| 从零项目 | 架构定稿后、契约冻结前后、**写第一行业务代码前** | 按四步全量生成 |
| 接手存量项目 | 盘点完成后 | **尊重现有代码风格**：以现状为准描述规则，与基线差异处标注「现状 / 目标 / 收敛方式（棘轮渐进）」，不一刀切重构 |
| 栈变更/新模块 | 变更发生时 | 增量修订对应节，走 ADR（若是选型级变更） |

## 4. 与 AGENTS 的关系（写入与引导必读）

- **条款写进生效层级**：全局适用 → 根 `AGENTS.md` 规范/红线段；仅某层级适用 → 对应子目录 `AGENTS.md`。每条 ≤1 行（禁止/必须/可判定），下层不复制上层。
- 规范**红线条目**（≤5 条，如「核心功能必须测试先行」「禁物理外键」「门禁链全绿才算完成」）摘进对应 AGENTS 层，每条 ≤1 行 + 指针 `.agents/rules/<文件> §x`。
- **正文留 `.agents/rules/`**（进该层级才读，不占每轮上下文）；根 AGENTS 文档索引与 AI 工作流登记全局规范必读引导（「改任何代码前必读」），子目录 AGENTS 登记本层正文必读指针（「改本模块代码前必读」）。
- 改规范 = 改条款所在载体一处（AGENTS 条款或 rules 正文）+ 核对两侧摘录与必读引导一致。

## 5. 维护与冲突处理

- 规范与代码现状冲突：列差异清单 → 小差异随手改（外科手术式），大差异走 ADR 决策 + 棘轮渐进，**禁止**为过门禁批量 `eslint-disable` / `noqa` / `type: ignore`。
- 每次版本 bump 复核：选型表、命令、阈值是否仍准确。
- 基线（assets/）是通用参考，**不随项目改动**；项目版规范（AGENTS 条款 + `.agents/rules/` 正文）才是 SSOT。
